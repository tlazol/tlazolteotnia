# blog-writer

筆者の口調で `content/blog/` に記事を書く。

## 書く前に

1. `content/blog/` から `date` が新しい記事を 3〜4 本読む。テーマが近い記事があればそれも読む。
   技術解説なら `why-not-just-try-yourself.md` や `understanding-harnesses-again.md`、雑記なら `tired-of-ai-questions.md` や `claude-code-from-my-phone.md` が参考になる。
2. 筆者が何を体験し、何を思ったのかが材料に書かれていなければ、書く前に聞く。体験や感想をでっち上げない。

## 文体

- 常体（だ・である）で書く。です・ます調にしない。
- 一人称は「僕」。冗談やタイトルでは「俺」も使う。
- 段落は 1〜3 文と短くし、段落の間に空行を入れる。一文だけの段落も多い。
- 書き出しは前置きを置かず、結論や現状から入る。
  - 「プログラマーを辞めようと思う。」
  - 「最近やめてよかったことがある。」
  - 「ハーネスのことを理解していたつもりだった。」
- 本音や感情は口語のまま書く。強い言葉も使ってよいが、多用しない。
  - 「まじで」「うーん。」「うーむ。」「しょうがないね。」「さすがやでぇ」「もういやだお…」「ばんざい！」
- 失敗や弱さを隠さない。「弱い人間なので自制では無理」「少なくとも僕には無理だ」のように書く。
- AI エージェントは「Claude Code 君」「AI 君」のように君付けで呼ぶことがある。
- 例え話はくだけたものでよい（「仕事は小さく小さく切って、ちょっとずつ食べていく」）。

## 表記

- 日本語と半角英数字の間には半角スペースを入れる（`Claude Code 君`、`30 分`、`2 つ`、`AI エージェント`）。
- 数字は半角。
- コマンド、ファイル名、スキル名、関数名はバッククォートで囲む。
- 強調の `**` は用語の初出などに絞って使う。

## 構成

- 見出しは `#` から始める。長い技術記事では `##` を使ってもよい。
- 比較や一覧は表か箇条書きにする。手順やコードはコードブロックで示す。
- 長い記事は冒頭に `## TL;DR` を置いてよい。短い雑記では置かない。
- 最後は「おわりに」か、見出しなしで締める。締めは一文の短い本音にする。
  - 「これからもよろしくな、ハーネス。」「ああ、コーディング、楽しかったな。」「そんな日々。」「以上。」
- 外部情報を引用したら、末尾に参考文献を置く。

```markdown
## 参考文献

1. <a id="reference-1"></a>[リンクの説明](https://example.com)
```

  本文からは `[[1]](#reference-1)` で参照する。

## 書かないこと

次の基準は、技術的な説明や経緯の説明にあたる部分に適用する。

- 読み物としての演出より、情報を伝えることを優先する。
- 問いかけ、溜め、決め台詞、抽象的な意味づけを足さない（「なぜ〜なのか。」「ここで重要になるのが〜だ」「これは単なる〜ではない」）。
- 説明部分の各文が、具体的な事実、判断、その根拠、条件、未確認事項のどれかを伝えているか点検する。
- 「〜が判断に関わる」「〜が重要になる」のように、何をどう判断するかを示さない文は削る。
- 削っても情報が失われない文は、言い換えずに削る。直前の内容を言い直すだけのまとめ文もこれに当たる。
- 緩急は説明の順序と段落分けで付け、演出のための文は足さない。

ただし、筆者の感情や本音（「まじで疲れる」「さみしいのだ」）は記事の中身なので削らない。締めの一言もこの口調の一部として残す。演出として削るのは、AI が説明に足した飾りの文だけ。

そのほかに書かないこと。

- 「人力で書いている」「この記事も自分で書いている」「『この文章を添削して』という指示をぐっと我慢して終わりとする」は、筆者が自分で書いた記事だけで使う定型文なので、AI が書く記事には入れない。
- 材料にない事実、数字、体験を足さない。分からない箇所は `TODO:` を残して筆者に確認する。

## タイトルと frontmatter

タイトルは口語で、少しネタっぽく、言い切るか感情をそのまま出す。

- 「AI がポエムすぎる」
- 「Skills の棚卸しするぞい！」
- 「俺は雰囲気でドキュメント DB で総数を取っている」
- 「AI との一問一答はもう飽きたんだお…」

ファイルは `content/blog/<slug>.md`。slug は英小文字のケバブケースにする。
frontmatter で使えるのは次のフィールドだけ。

```markdown
---
title: "タイトル"
date: "YYYY-MM-DD"
description: "記事の内容を 1〜2 文で。本文と同じ口調でよい。"
tags: ["AI", "Claude Code"]
draft: true
---
```

- `draft` は `true` で作る。公開は筆者が決める。
- tags は既存記事で使われているタグを優先する（`grep -h '^tags' content/blog/*.md` で確認する）。

## 表記の仕上げ

次の基準で表記を整える。

- 文末を揃える（常体に統一する）。
- 日本語の中の半角英字・数字の前後に半角スペースを入れる。
- 誤字、脱字を直す。
- 製品名やサービス名は公式の表記にする（`Cloudflare`、`GitHub`、`TypeScript` など）。

## 筆者の原稿を添削するとき

筆者が自分で書いた原稿を「添削して」「整えて」と渡されたときは、新しく書くときとは扱いを変える。

- 原稿を軽く整えるのはよいが、大きく書き直さない。口調も構成も筆者のものを残す。
- 直すのは表記、スペース、誤字、ぎこちない文法に絞り、「表記の仕上げ」の基準を使う。
- 「書かないこと」に当たる文を見つけたら、勝手に書き換えず、削除の提案として示す。
- 「人力で書いている」などの定型文は、筆者が書いた記事なので残す。
- 原稿にない事実を足さない。判断の中身が分からない箇所は筆者に確認する。

## 書いた後

1. 「書かないこと」に当てはまる文がないか読み直し、該当する文は言い換えずに削る。
2. 「表記の仕上げ」の基準で表記を揃える。
3. OG 画像を作り、検証する。

```bash
npm run og
npm run validate:content
```

4. 筆者に確認してほしい箇所（`TODO:` や推測で書いた部分）を一覧にして伝える。
